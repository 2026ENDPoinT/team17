# crawler: 교내 게시판 장학금 공지 수집

교내 게시판 목록에서 제목에 장학금 키워드가 있는 글을 골라 상세 페이지를 읽고, 글 1건마다 `data/raw/{bidx}.json` 파일 1개를 만든다.

- 담당: 크롤링 담당 (이 폴더와 `data/raw/`는 크롤링 담당만 고친다)
- 받는 사람: 분류 담당 (`classifier/`가 `data/raw/`를 읽는다)
- 형식의 기준: [`data/raw/_sample.json`](../data/raw/_sample.json). 필드를 바꾸면 샘플과 이 문서를 같이 고치고 팀에 알린다.

## 실행

저장소 루트에서 실행한다. 외부 라이브러리는 첨부 추출용 `pypdf`, `hwp-hwpx-parser` 두 개다 (2026-11-13 팀에 알리고 추가).

```bash
uv run python crawler/crawl.py --mode offline   # 저장된 HTML만 사용 (개발·테스트용, 학교 서버 요청 없음)
uv run python crawler/crawl.py --mode record    # 학교 서버에서 받고, HTML을 crawler/fixtures/에 저장
uv run python crawler/crawl.py --mode live      # 학교 서버에서 받기만
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--out 폴더` | `data/raw` | 결과를 쓸 폴더. 녹화나 시험용 수집이 데모 데이터(`data/raw`)를 바꾸지 않게 할 때 쓴다 |
| `--since-days N` | 60 | 최근 N일 글까지 모은다 |
| `--max-pages N` | 10 | 게시판마다 목록을 최대 N쪽까지 읽는다. 기간을 늘리면 같이 늘린다 |

분류 규칙 시험용 6개월치(`data/raw_test/`)는 이렇게 만들었다. **데모 화면에는 쓰지 않는다.** 2026-11-13 기준 공지 238건(2026-05 ~ 11), 첨부 텍스트 297개, 재게시 19건이다. 받는 데 약 17분 걸렸다.

```bash
uv run python crawler/crawl.py --mode record --out data/raw_test --since-days 183 --max-pages 40
```

- `crawler/fixtures/`는 Git에 올리지 않는다. 원본 HTML과 첨부 원본(`fixtures/files/`)에 연락처가 그대로 있기 때문이다. 처음 한 번 `record`로 만든다.
- 첨부 107개를 처음 받는 데 약 4분 걸린다. 한 번 뽑은 첨부는 다시 받지 않는다.
- 게시판 16곳의 최근 60일, 71건을 처음 받는 데 약 2분 30초 걸린다 (2026-11-13). 같은 호스트에는 1초 간격으로 요청한다.
- 이미 받은 글은 최근 14일 안의 글만 다시 읽는다. `content_hash`가 바뀌면 덮어쓰고 `수정됨`으로 출력한다. offline 모드에서는 내용이 같으면 파일을 다시 쓰지 않는다 (`last_checked`는 학교 서버를 실제로 확인한 시각만 남긴다).
- 같은 `bidx`가 두 게시판에 나오면(미러 게시판) `BOARDS`에서 먼저 나온 게시판 것만 저장한다.

| 파일 | 역할 |
|---|---|
| `config.py` | UA, 요청 간격, 키워드, 수집 기간, 게시판 목록 |
| `fetch.py` | HTML 받기 (live / record / offline) |
| `parse.py` | 목록·상세 HTML 파싱 (네트워크 없음) |
| `privacy.py` | 연락처·학번·마스킹된 이름·결과 공지 이름 명단 지우기 |
| `attachments.py` | 첨부 받아서 텍스트 뽑기 (pdf, hwp, hwpx, docx), 결과 공지 첨부 건너뛰기 |
| `dedup.py` | 재게시 표시 (`duplicate_of` 정하기, 네트워크 없음) |
| `crawl.py` | 위를 연결해 `data/raw/{bidx}.json` 저장 |

## `data/raw/{bidx}.json` 필드

샘플 값은 **지어낸 예시**다. 실제 공지가 아니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `_sample` | bool | 샘플 파일에만 `true`. 실제 수집 파일에는 없다. 분류 쪽은 이 값이 있는 파일을 건너뛴다 |
| `bidx` | int | 글 번호. 전역 고유이고 파일 이름으로 쓴다 |
| `bnum` | int | 게시판 번호. 첨부 경로(`/storage/{site}/bbs/{bnum}/…`)에 쓰인다. 샘플은 `0` |
| `site` | string | 호스트 앞부분 (`www`, `ice`, `mech` …). `tools/research/boards.txt` 첫 칸과 같다 |
| `board` | string | 게시판 이름 (`장학공지`, `공지사항` …) |
| `url` | string | 원문 상세 주소. 화면의 "원문 보기" 링크로 쓴다 |
| `title` | string | 목록에 보이는 제목 그대로. "(마감)", "연장" 같은 수정도 그대로 둔다 |
| `posted_date` | string | 게시일 `YYYY-MM-DD`. 사이트에 시각이 없어서 날짜만 있다 |
| `pinned` | bool | 목록 상단 고정 공지인지 |
| `duplicate_of` | int \| null | 다른 게시판에 다시 올린 글이면 **대표 글의 `bidx`**, 대표 글이거나 혼자인 글이면 `null`. 내용이 같은 복사본만 표시한다. 아래 "재게시 표시" 참고 |
| `matched_keywords` | string[] | 제목에서 걸린 키워드 (`장학`, `근로`, `학자금`, `등록금`. 취업정보 게시판은 `장학`만). 장학 전용 게시판 글은 비어 있을 수 있다 |
| `body_text` | string | 본문(`td.cont`) 텍스트. 줄바꿈 유지, HTML 태그 제거. **이메일·전화번호(내선·대표번호 포함)는 `[연락처]`, 학번은 `[학번]`, 마스킹된 이름(홍*동)은 `[이름]`, 결과 공지의 이름 나열("선발결과 : 홍길동, 김철수 (이상 2명)")은 `[명단 삭제]`로 바꾼 뒤** 저장한다. 표나 한 줄에 한 명씩 쓴 명단은 못 잡을 수 있다. 본문이 없으면 `""` |
| `has_images` | bool | 본문에 이미지가 있는지. 포스터만 있는 글(본문 `""` + `true`)을 분류 쪽이 "원문 확인 필요"로 넘기는 데 쓴다 |
| `attachments` | object[] | 첨부 목록. 없으면 `[]`. 파일 자체는 저장하지 않는다 |
| `attachments[].name` | string | 화면에 보이는 첨부 이름 |
| `attachments[].ext` | string | 소문자 확장자 (`pdf`, `hwp`, `hwpx` …) |
| `attachments[].url` | string | 원문 첨부 주소 (다시 배포하지 않고 링크만 둔다) |
| `attachments[].text` | string \| null | 첨부에서 뽑은 텍스트. 본문과 같은 개인정보 제거를 거친다. HWP 표는 `| 칸 | 칸 |` 모양으로 나온다. 최대 2만 자. `ok`가 아니면 `null` |
| `attachments[].text_status` | string | `ok` 뽑음 / `empty` 글자 없음(스캔 PDF 등) / `failed` 실패 / `unsupported` 지원 안 하는 형식(jpg, xlsx, zip) / `skipped_result` 결과 공지라 안 뽑음 / `skipped_large` 20MB 초과 / `not_extracted` 아직 안 함 |
| `content_hash` | string | `sha256:` + `sha256(title + "\n" + body_text)`. 다시 읽었을 때 값이 바뀌면 글이 수정된 것이다 |
| `first_seen` | string | 처음 수집한 시각 (ISO 8601, `+09:00`) |
| `last_checked` | string | 마지막으로 다시 읽은 시각 |

## 실제 수집 결과로 확인한 것 (본부 장학공지 37건, 2026-11-13)

학과 게시판 등 34건을 더한 71건도 모두 샘플과 필드가 같다. 학과 쪽 34건은 본문 100자 미만이 6건(18%)으로 본부보다 적다.

- 37건 모두 샘플과 필드 이름·타입이 같다.
- 본부 장학공지는 하위 게시판 2개(장학공지 `bnum=5233`, 근로장학 `bnum=57138`)를 합쳐 보여 준다. 그래서 `bnum`은 글마다 다르다.
- **본문이 100자 미만인 글이 16건(43%)이다.** 대부분 교외 "(홍보)" 공지이고, 내용은 포스터 이미지(`has_images: true`)나 첨부에 있다. 전체 공지 평균(18%)보다 훨씬 높다. 금액·마감·조건을 뽑으려면 첨부나 이미지를 봐야 하는 글이 많다.
- 첨부가 있는 글은 30건(81%)이다. 형식은 pdf 22, hwp 21, hwpx 7, docx 3, jpg 2, xlsx 1개다.
- 제목에 키워드가 없는 글이 2건 있다 (시험지원인력 모집, 아동돌봄 지원사업). 장학 게시판이라 거르지 않고 넣었다. 장학금인지는 분류 단계에서 판단한다.
- 저장된 본문과 제목에 전화번호·이메일 패턴이 남은 글은 없다. 13건에서 `[연락처]`로 바꿨다.

## 수집 게시판 (`config.BOARDS`, 16곳)

2026-11-13에 게시판 136곳의 최근 60일 목록을 실측해서 골랐다 (`tools/research/volume.py`).

| 구분 | 게시판 | 고른 이유 |
|---|---|---|
| 장학 전용 (키워드로 거르지 않음) | 본부 장학공지, 건축학부 장학금 | 게시판 전체가 장학금 |
| 학부 공지 (제목 키워드로 거름) | 본부 대학공지, 산업공학과, 건설시스템공학과, 전기정보공학과, 지능형반도체공학과, 안전공학과, 안경광학과, GTM전공, 컴퓨터공학과, 경영학전공, 국제대학 | 본부 공지를 다시 올린 것이 아니라 **학과가 직접 올린** 장학금 공지가 있었다 |
| 취업정보 (`장학`만) | 기계·자동차공학과, 기계시스템디자인공학과, MSDE학과 | 기업 연구장학생 모집 (현대모비스 등) |

- **넣지 않은 것**: 대학원 공지 게시판(팀 결정: 학부생 대상), 본부 공지를 다시 올리기만 한 학과 게시판(어의·가족장학생 등이 15곳 이상에 똑같이 올라옴), 학사공지(등록금 납부 안내뿐).
- 학과 게시판을 더 넣으면 재게시가 많아진다. 아래 "재게시 표시"가 내용이 같은 복사본을 표시한다.

## 결과 공지의 이름 명단

산업공학과 "선발 결과 알림"에 마스킹되지 않은 이름 3명이 본문에 있었다. `privacy.py`에 명단 줄 규칙을 넣어 `[명단 삭제]`로 바꿨다. 처음 만든 규칙은 "미선발자", "수혜자는" 같은 일반 문장까지 지워서, 명단 줄 조건을 "선발결과 :", "합격자 명단 :", "(이상 N명)"처럼 좁혔다. 71건 모두 확인했을 때 남은 명단과 잘못 지운 문장은 없었다.

## 재게시 표시 (`dedup.py`)

학과가 본부·다른 학과 공지를 다시 올리면 `bidx`가 새로 생긴다. 크롤러는 **내용이 같은 복사본만** `duplicate_of`에 대표 글 번호를 적는다. 파일은 지우지 않는다. 같은 장학금의 다른 공지(모집·수정·완료)를 이벤트로 묶는 일은 라벨링 다음 단계(이벤트 묶기)가 한다 (2026-11-13 팀 결정).

- 수집이 끝날 때마다 `data/raw` 전체를 다시 보고 표시한다.
- **후보**: 서로 다른 게시판 / 게시일 60일 이내 / 정규화 제목 유사도 0.7 이상
- **확인** (둘 중 하나):
  - 첨부 파일 이름 목록이 완전히 같다. 본문 유무와 상관없다. 학과가 본문 대신 포스터만 올리고 첨부는 그대로 다는 경우가 있다.
  - 둘 다 본문이 있고(30자 이상), 본문 유사도가 0.95 이상이며, **본문 속 숫자(날짜·금액·차수)가 모두 같다**.
- 대표 글: 본부(`www`) 글 > 먼저 올라온 글 > `bidx`가 작은 글. 각 글은 **대표 글과 직접** 비교한다 (사슬 묶기 안 함).
- **제목 정규화** (`normalize_title`, 후보를 고를 때만 씀): 저장하는 `title`은 원본 그대로이고, 비교할 때 만드는 임시 사본에만 적용한다. 괄호 내용을 세 층으로 나눈다 (2026-11-14, 이벤트 묶기 단계와 함께 정함).
  - **항상 지움**: 날짜·기한(~11/6, 요일), 상태 꼬리표(마감, 홍보, 수정, 연장, 추가, 교체 …), 게시판 분류 표시(한 글자 괄호 "(재)"·"(善)", 정확히 "장학"·"발전기금"). "(수정 3차)"의 3차는 몇 번째 수정인지라서 차수로 보지 않고 지운다.
  - **목적에 따라 다름**: 학교 부서·대상([학부], [도서관], (GTM전공) …). 재게시 판정은 학과가 다시 올리며 붙이거나 바꾸므로 지운다(`drop_units=True`, 기본값). 이벤트 묶기는 "[도서관] 국가근로장학생 모집"과 "[생활협동조합] …"이 다른 모집이므로 남긴다(`drop_units=False`).
  - **항상 남김**: 재단·장학회·회사 이름(상태 꼬리표와 같이 있어도), 차수·유형·금액, 과목·분야("(수학)", "(한국어)"), 모르는 내용.
  - 처음에는 괄호 안을 모두 지웠다. 그래서 "[해성문화재단] 장학생 선발"과 "어의장학생 선발"이 0.91로 비슷했고(지금 0.78), "튜터 장학생(한국어)"와 "(수학)"이 같아졌다. 그래도 제목만으로는 다 막지 못하므로(등록금 1차·2차는 0.96) 최종 판단은 본문·첨부로 한다.
- **원칙: 애매하면 묶지 않는다.** 잘못 묶으면 서로 다른 장학금 하나가 대표 글 뒤로 숨는다. 못 묶으면 같은 공지가 두 번 보일 뿐이고 검수 때 고칠 수 있다.

**이렇게 정한 이유** (6개월 데이터 238건으로 시험)
- 처음에는 제목만 봤다 (유사도 0.9, 숫자 일치, 14일 이내). 14일은 실측이 아니라 짐작이었다.
- 제목만 보면 "[해성문화재단] 장학생 선발"과 "어의장학생 선발"처럼 다른 공지가 묶였다. 괄호를 지우는 정규화가 재단 이름이나 "(2차)"까지 지웠기 때문이다.
- 내용이 같은 재게시 21쌍은 모두 제목 유사도도 0.9 이상이었다. 제목을 크게 바꿔 다시 올린 경우는 없었다. 그래서 제목은 후보를 고르는 데만 쓰고(0.7, 여유를 둔 값), 판단은 내용으로 한다.
- 등록금 1차(8월)와 2차(9월) 공지는 같은 틀에 날짜만 달라 본문 유사도가 0.99였다. 그래서 본문 속 숫자도 같아야 한다.
- 실제 재게시의 게시일 차이는 0~13일이었다 (18쌍 중 12쌍이 같은 날). 내용으로 확인하므로 기간은 60일로 넉넉히 둔다.
- 대가: 학과가 본문을 새로 써서 다시 올린 글 2건("외국인 장학생 어학성적 제출", "등록금 분할납부 실시")은 표시되지 않는다.

결과 (2026-11-13): `data/raw` 71건 중 재게시 6건 (현대모비스 연구장학생 2, 어의장학생 2, 가족장학생 1, 어의·가족장학금 1), `data/raw_test` 238건 중 19건. 틀린 표시는 `data/reviewed/`에서 고친다.

## 첨부 텍스트 (`attachments.py`)

본부 장학공지는 본문이 거의 없는 글이 43%여서 첨부를 읽는다 (2026-11-13).

- 형식별 방법: pdf는 `pypdf`, hwp·hwpx는 `hwp-hwpx-parser`, docx는 표준 라이브러리(zip 안의 XML)로 읽는다.
- **결과 공지의 첨부는 받지 않는다.** 제목에 결과·지급완료·명단·합격자·선발자·선정자가 있으면 `skipped_result`로 표시한다. 명단 파일일 가능성이 높아서다.
- 뽑은 텍스트는 본문과 같은 `privacy.scrub()`을 거쳐 `data/raw`에 저장한다. 파일 원본은 저장하지 않는다.
- 2026-11-13 결과: 첨부 113개 중 `ok` 105, `empty` 2, `unsupported` 6. 2만 자에서 잘린 첨부가 2개다. `data/raw` 전체 크기는 약 0.8MB다.
- 점검 결과: 첨부 텍스트에 이메일·전화번호·학번·주민번호 패턴은 남지 않았다. "성명"은 모두 빈 신청서 양식의 칸 이름이었다. 계좌번호 1건은 재단의 장학금 반납 계좌(기관 계좌)라 그대로 두었다.

## 학교 서버가 응답을 끊는 문제

6개월치를 받을 때 페이지 369개 중 10개가 중간에서 잘려 왔다. 그래서 본문이 빈 채로 저장된 글이 5건 있었다. 잘린 페이지는 모두 상세 페이지였고, 목록이 잘려 글을 놓친 경우는 없었다. 이렇게 고쳤다.

- `fetch.py`: HTML이 `</html>`로 끝나지 않으면 잘린 것으로 보고 다시 받는다 (간격을 2초, 4초, 8초로 늘림).
- `crawl.py`: 본문 위치를 못 찾은 글은 저장하지 않는다. 빈 본문이 기존의 정상 파일을 덮어쓰지 않게 하려는 것이다.
- 잘린 10개는 다시 받아 fixture를 고쳤고, `data/raw_test`를 offline으로 다시 만들었다. `data/raw`는 바뀐 것이 없다.
