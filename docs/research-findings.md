## 핵심 요약

1. **학교 공식 앱이 이미 공지 푸시를 제공한다.** 서울과기대 "스마트캠퍼스" 앱에서 대학공지, 학사, 장학, 취업 공지를 볼 수 있고 구독 메시지 기능도 있다. 우리 서비스는 공식 앱이 하지 않는 일로 차별화해야 한다. 예를 들어 **학과·단과대 게시판 통합, 관심 분야 분류, 마감일 정리** 같은 것이다.
2. **다른 대학에는 비슷한 학생 제작 서비스가 이미 여럿 있다.** 건국대 쿠링, 광운대 KW 알리미, 여러 대학을 지원하는 유니뷰 등이다. 서울과기대 전용 서비스는 찾지 못했다.
3. **`bidx`는 글마다 고유하지만, 다른 게시판에 다시 올린 글은 새 `bidx`를 받는다.** 따라서 `bidx`만으로는 중복을 다 잡을 수 없고, 제목 유사도 비교가 꼭 필요하다. (직접 확인)
4. **RSS는 없다.** HTML을 파싱해야 한다. (직접 확인)
5. **공개 정보를 크롤링한 것은 형사상 무죄라는 대법원 판례가 있다.** 다만 같은 사건의 민사에서는 손해배상 책임이 인정됐다. 공지를 상업적으로 대량 복제하지 않는 설계가 중요하다.
6. **카카오 알림톡은 사업자 등록이 필요하다.** 학생 프로젝트라면 웹 푸시, 텔레그램, 디스코드, 이메일이 현실적이다.
7. **공지량은 하루 약 16건(학부 기준), 한 달 약 470건이다.** 136개 게시판 중 57개는 최근 30일 동안 새 글이 없었다. 처리량은 작아서 서버나 LLM 비용은 걱정할 수준이 아니다. (직접 확인, 6.1절)
8. **같은 공지가 여러 학과에 최대 10번까지 다시 올라온다.** 제목이 똑같은 사본만 세어도 한 달에 82건이다. 제목이 조금씩 다른 사본까지 치면 더 많다. 중복 묶기는 MVP 필수 기능이다. (직접 확인, 6.2절)
9. **본문이 사실상 없는 공지는 18%다.** 그중 포스터 이미지만 있는 글이 13%, 첨부파일만 있는 글이 7%다. 첨부가 달린 글은 47%다. 제목과 본문만으로 분류하는 MVP로도 80% 이상은 처리된다. (직접 확인, 6.3절)
10. **공지는 올라온 뒤에도 수정된다.** "(마감)", "신청기한 연장", "(장소변경)"처럼 제목이 바뀐다. 상세 페이지에는 수정일이 없어서 최근 글을 다시 읽어 비교해야 한다. (직접 확인, 2.6절)

## 2. 학교 사이트 기술 조사 (직접 확인)

### 2.1 `bidx`(글 번호)의 성질

| 확인 내용 | 결과 |
|---|---|
| 같은 `bidx`에 다른 제목이 붙은 경우 | 없었다. → **글 ID로는 전역 고유**하다고 봐도 된다 |
| 미러 게시판 (본부 취업공지 ↔ 취업진로본부, 본부 현장실습 ↔ 현장실습지원센터) | **같은 `bnum`과 같은 `bidx`**를 쓴다. → `bidx`로 중복 제거가 된다 |
| 학과가 본부 공지를 다시 올린 경우 | **새 `bidx`**를 받는다. 예: "2026학년도 2학기 수강신청 교과목 철회 안내"가 본부 학사공지에서는 `bnum=6112, bidx=896637`, 경영학전공 공지에서는 `bnum=56506, bidx=897303` |

**결론**: 중복 제거는 2단계로 해야 한다.
1. `bidx`가 같으면 같은 글이다. (미러 게시판)
2. `bidx`가 달라도 제목이 거의 같고 날짜가 가까우면 같은 공지로 묶는다. (학과 재게시)

### 2.2 RSS·피드

- `?do=rss`, `/rss/` 등 흔한 경로를 시도했지만 RSS를 제공하지 않는다. 페이지에 `<link rel="alternate" type="application/rss+xml">`도 없다.
- 따라서 **HTML 목록 페이지를 파싱**해야 한다.

### 2.3 글 상세 주소 형식이 게시판마다 조금씩 다르다

| 형식 | 예 |
|---|---|
| `?do=commonview&bnum=...&bidx=...` | 본부, 대부분의 학과 |
| `?do=view&bnum=...&bidx=...` | 일부 학과 (예: 건축기계설비공학과) |
| `?bgu=view&idx=...` | 건축학전공 (별도 PHP CMS) |

파서는 `bidx` 또는 `idx` 값을 정규식으로 뽑는 방식으로 만들면 대부분 처리된다.

### 2.4 학사일정과 학생활동 통합캘린더

- **학사일정** (`https://www.seoultech.ac.kr/life/sch/common/`): "날짜 범위 + 내용" 형태의 표로 렌더링된다. 예: `2026.11.18 ~ 11.18 2학기 수업일수 3/4선`. 파싱하기 쉽다. **마감 알림 기능에 활용할 수 있다** (수강철회 기간, 등록금 납부 기간 등).
- **학생활동 통합캘린더** (`https://www.seoultech.ac.kr/intro/calendar/`): ~~`ajax.jsp?menu=77346`으로 데이터를 받아온다~~ → **정정 (2차 조사)**: 이 요청은 접속 로그 기록용이다. 캘린더는 `sdate`·`edate`·`size`·`category`를 POST로 보내는 일반 검색 폼이고, 결과는 서버에서 HTML로 렌더링된다. 다만 **2026년 3~12월 전체에 등록된 일정이 1건뿐**이라 사실상 쓰이지 않는다. 데이터 출처로는 쓸 수 없다.
  - 대신 이 캘린더의 **카테고리 목록**(대학및학과행사, 모집, 부서행사, 설문, 수업, 어학, 일반공지, 장학, 취업, 필수, 학부모, 학사일정, 특강/교육, 기타)은 학교가 직접 정한 분류 체계라서 **우리 태그 설계의 출발점**으로 쓸 만하다.

### 2.5 저작권 표시

- 본부 공지 상세 페이지와 학과 공지 목록에서 **공공누리(KOGL) 표시를 찾지 못했다.** 3.2절 참고.

### 2.6 크롤러를 만들 때 알아야 할 세부 사항 (2차 조사, 직접 확인)

| 항목 | 결과 | 크롤러 설계에 주는 영향 |
|---|---|---|
| **페이지 이동 파라미터** | 실제로 동작하는 것은 `?page=N`이다. 상세 링크에 붙어 있는 `nowpage=N`은 **무시된다** (1페이지가 다시 나옴). `size=` 파라미터도 무시되고, 목록 크기는 게시판마다 10~20개로 고정이다. | `page`를 써야 한다. `nowpage`로 짜면 에러 없이 1페이지만 반복 수집한다. |
| **목록 레이아웃 2종** | 대부분은 `<table class="tbl_list">`의 `<tr>` 행이다. 생활관·신소재공학과 학과소식 등은 카드형 `<div class="blog_list"> <div class="list">` 구조다. 고정 공지는 표에서는 번호 칸이 숫자가 아니고, 카드형에서는 `ico_notice` 아이콘이 붙는다. | 파서를 2개 만들거나, `bidx`가 있는 블록을 찾는 범용 파서를 만든다. |
| **상세 본문 위치** | `<td class="cont">` (본부는 `class="cont"`가 앞, 학과는 `colspan` 뒤에 오기도 한다) | 속성 순서에 의존하지 않는 선택자(BeautifulSoup `td.cont`)를 쓴다. |
| **첨부파일** | 화면에서는 JS(`downloadfile()` → `/hcm/bbs/bbs_download.jsp` POST)로 받지만, 실제 파일은 `/storage/{사이트}/bbs/{bnum}/{저장파일명}`에 **정적 파일로 공개**돼 있어 GET으로 바로 받아진다. 본부에는 Synap 문서 미리보기(`view.seoultech.ac.kr`)도 있다. | 첨부 분석 단계에서 다운로드가 쉽다. 반대로 우리 서비스는 **첨부를 다시 호스팅하지 말고 원문 링크로 보낸다.** |
| **날짜** | 목록과 상세 모두 날짜만 있고 **시각이 없다**. | 같은 날 글의 순서는 `bidx` 크기로 정한다. |
| **`bidx` 순서** | 같은 게시판에서 `bidx`가 클수록 최신인 경우가 377쌍 중 367쌍(97%)이다. 10쌍은 날짜가 거꾸로였다. | "처음 보는 `bidx`인가"로 새 글을 판정한다. "마지막으로 본 `bidx`보다 큰가"로 판정하면 일부를 놓친다. |
| **수정** | 30일 동안 제목 549건 중 18건에 "(수정)", "연장", "(마감)", "(장소변경)" 등이 붙었다. 상세 페이지에 **수정일 표시가 없다.** | 최근 2주 정도의 글은 주기적으로 다시 읽고, 제목·본문 해시가 바뀌면 갱신한다. |
| **TLS·인코딩** | 수집 대상 호스트 71개 모두 인증서 검증을 정상 통과하고 모두 UTF-8이다. 응답은 평균 0.1초다. | 특별한 처리가 필요 없다. (예외: iac는 이전 조사에서 TLS 오류) |

### 3.1 크롤링 관련 판례 (출처 확인)

**야놀자 ↔ 여기어때 사건 (대법원 2021도1533, 2022년 확정)**
- 여기어때 측이 야놀자 API 서버에 크롤링 프로그램으로 접근해 숙박업소 정보를 복제한 사건이다.
- **형사**: 정보통신망법 위반(침입), 저작권법(데이터베이스권) 위반, 컴퓨터등장애업무방해 모두 **무죄**가 확정됐다.
  - 수집한 정보가 대부분 이용자에게 공개된 정보였다.
  - 약관이나 기술적 조치로 크롤링을 금지하지 않았다. 접근권한은 객관적으로 드러난 사정으로 판단한다.
  - 데이터베이스의 일부만 수집했다.
- **민사**: 같은 행위에 대해 **손해배상 책임이 인정됐다** (1심 10억 원). 경쟁사의 데이터를 복제해 영업에 쓴 점이 문제가 됐다.

**우리 프로젝트에 대한 시사점**
- 학교 공지는 공개 정보이고, robots.txt나 약관으로 크롤링을 금지하지 않는다 ([notice-sources.md](notice-sources.md) 4.4절). 형사 판례의 기준에 비추면 위험이 낮은 편이다.
- 다만 민사 판결처럼 **"남의 데이터를 복제해 영업에 쓰는"** 구조가 되면 문제가 될 수 있다. → 본문 전체를 복제하지 말고, 제목·요약·원문 링크로 **학교 사이트로 트래픽을 보내는 구조**가 안전하다.
- 별개로, 2026년 1월에는 네이버 부동산 DB 사건에서 데이터를 정리·가공하는 데 인력과 비용을 들였다면 보호받을 수 있다는 취지의 특허법원 판결이 보도됐다. 데이터베이스 보호에 대한 판단은 계속 바뀌고 있다.

## 5. 기술 도구

### 5.1 HWP/HWPX 첨부파일 텍스트 추출 (출처 확인)

실측해 보니 본문 없이 첨부만 있는 공지는 7% 정도다(6.3절). 첨부가 달린 글은 47%이고, 형식은 PDF 67건, HWP 54건, HWPX 1건 순이었다. 그러니 첨부 분석을 한다면 **PDF와 HWP 둘 다** 지원해야 한다. 2단계(첨부 분석) 기능을 할 때 후보가 되는 라이브러리다.

| 라이브러리 | 지원 형식 | 특징 |
|---|---|---|
| [hwp-hwpx-parser](https://pypi.org/project/hwp-hwpx-parser/) | HWP, HWPX | 순수 Python, JVM 불필요, 텍스트·표·각주 추출 (읽기 전용) |
| [helper-hwp](https://pypi.org/project/helper-hwp/) | HWP 5.x, HWP 97, HWPX | 문단·표 단위 순회 API |
| [python-hwpx](https://github.com/airmang/python-hwpx) | HWPX | 읽기·편집·생성, 아직 Alpha |
| pyhwp | HWP5 | 오래된 라이브러리, 일부 스트림 미지원 |
| pyhwpx | – | Windows + 한/글 설치 필요 → **서버용으로 부적합** |

> 첨부파일에는 선발자 명단(이름·학번) 같은 개인정보가 있을 수 있다. 그래서 **결과 공지(선발 결과, 지급완료, 명단 등)의 첨부는 추출하지 않는다.** 나머지 첨부의 텍스트는 연락처·학번·이름 명단을 지운 뒤 `data/raw`에 저장하고, 분류에만 쓴다. 화면에는 첨부 텍스트를 그대로 보여 주지 않는다. (2026-11-13 결정. 실제로는 `pypdf`와 `hwp-hwpx-parser`를 쓴다. 자세한 내용은 `crawler/README.md`)

### 5.2 크롤러 실행 환경

- **GitHub Actions 예약 실행(cron)**: 무료로 시작하기 좋다. 다만 실행 간격은 최소 5분이고 혼잡할 때는 지연될 수 있으며, 공개 저장소는 60일 동안 활동이 없으면 예약 실행이 자동으로 꺼진다. 공지 수집은 하루 몇 번이면 충분하므로 큰 문제는 아니다.
- 수집 결과는 DB(예: SQLite 파일, 무료 등급 PostgreSQL)에 저장하고, 서비스 서버는 DB만 읽게 분리한다.

### 5.3 분류용 LLM

- 키워드 규칙으로 먼저 거르고 애매한 것만 LLM에 보내면 비용이 크게 줄어든다. 추출값에는 근거 문장을 붙인다. ([project-risks.md](project-risks.md) 1절)
- 하루 신규 공지는 학부 기준 약 16건, 중복을 묶으면 그보다 적다(6.1절). 그래서 **작고 저렴한 모델**로 충분할 가능성이 높다. 과거 글을 한꺼번에 처리할 때는 배치 처리 기능을 쓴다.
- 구체적인 모델과 가격은 개발을 시작할 때 각 회사의 공식 문서로 확인한다.

| 제목에 마감 표현 (`~11/18`, "까지" 등, 549건 중) | 19% | 제목만으로도 일부 추출 가능 |
| 외부 신청폼 링크 (구글폼, 네이버폼 등) | 9% | "신청하기" 바로가기를 보여줄 수 있다 |
| 이메일 주소 포함 | 16% | 저장·노출 전에 제거해야 한다 |
| 전화번호 포함 | 18% | 담당 부서 번호가 대부분이다 |
| 마스킹된 이름 (`김*성` 형식) 포함 | 2% | 선발자 명단, 제적 안내 등. **본문 전체를 다시 보여주면 안 되는 이유** |

**시사점**
- 제목 + 본문 텍스트만으로 분류하는 MVP로 **약 80%의 글을 처리할 수 있다.** 나머지 20%는 "원문 보기"로 넘기고, 이미지·첨부 분석은 2단계로 미룬다.
- 2단계에서 하나를 고른다면, **포스터 이미지 인식(13%)이 첨부 텍스트 추출(7%)보다 효과가 크다.**

### 6.5 기술 검토 결론: 지금 수준이면 충분한가

**MVP(본부 + 학과 게시판 수집, 제목·본문 분류, 원문 링크, 알림)를 만드는 데 필요한 기술 조사는 충분하다.** 크롤링을 막는 장치가 없고, 사이트 구조는 거의 하나의 CMS로 통일돼 있으며, 처리량도 작다.

개발 전에 남은 기술적 불확실성은 아래와 같다.

| 불확실성 | 왜 중요한가 | 확인 방법 |
|---|---|---|
| **해외 IP 접근 여부** | GitHub Actions 러너는 해외(미국) 데이터센터에서 돈다. 국내 대학 사이트 중에는 해외 IP를 막는 곳이 있다. 막히면 실행 환경을 바꿔야 한다. | GitHub Actions에서 목록 페이지 1개를 요청해 보는 워크플로를 한 번 돌린다 (5분 작업) |
| **중복 묶기 기준** | 너무 느슨하면 다른 공지가 합쳐지고, 너무 엄격하면 사본이 남는다. | 6.2절의 실제 사례로 정규화 + 유사도 임계값을 테스트한다 |
| 건축학전공(archidesign) 파서 | 별도 CMS라서 이번 측정에서도 0건으로 나왔다. | MVP에서 빼거나 전용 파서를 만든다 |
| 취업진로본부 일반채용 | 일반 게시판 형식이 아니다. | 본부 채용정보·학과 취업정보로 대체할 수 있는지 본다 |
| 미래에너지융합학과 대학원공지·취업정보, 생활관 공지사항2 | 이번 파서로 0건이 나왔다 (구조 차이 또는 빈 게시판, 미확인). | 브라우저로 열어 확인한다 |

**권장 수집 설계 (실측 근거 반영)**
1. 게시판 목록은 설정 파일(YAML)에 두고, 레이아웃 유형(`table`/`card`/`api`)과 상태(활발/휴면)를 함께 적는다.
2. 목록은 `?page=1`만 주기적으로 읽는다. 처음 보는 `bidx`가 나오면 상세를 읽는다. 처음 구축할 때만 `page`를 늘려 과거 글을 채운다.
3. 최근 14일 글은 하루 한 번 다시 읽어 제목·본문 해시가 바뀌었는지 본다 (수정 감지).
4. 저장 전에 이메일·전화번호·마스킹 이름을 제거하고, 화면에는 제목·요약·원문 링크만 보여준다.
5. 중복은 `bidx` 일치 → 정규화 제목 유사도 순으로 묶고, 대표 글은 본부 게시판 글로 한다.
