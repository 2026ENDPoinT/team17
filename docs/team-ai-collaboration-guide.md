# AI와 함께하는 팀 개발 가이드

> 작성일: 2026-11-13
> 대상: team17 팀원 전원
> 저장소: https://github.com/2026ENDPoinT/team17

여러 사람이 각자 AI 코딩 도구(Claude Code, Cursor, Copilot, ChatGPT 등)를 쓰면서 한 저장소에서 함께 개발할 때, **시작 전에 맞춰야 할 것**과 **알아두면 좋은 것**을 정리한 문서다.

핵심은 한 문장으로 요약된다.

> **AI는 각자 쓰지만, AI가 참고하는 규칙과 맥락은 저장소 하나에 모아서 모두가 같은 것을 보게 한다.**

AI는 대화가 끝나면 맥락을 잊고, 팀원마다 다른 대화를 한다. 같은 기능을 부탁해도 사람마다 다른 라이브러리, 다른 폴더 구조, 다른 코드 스타일이 나온다. 그래서 사람끼리 하는 협업보다 **미리 정해 두는 것**이 훨씬 중요하다.

## 1. 시작 전에 반드시 맞출 것

아래 항목을 정하지 않고 시작하면, 각자의 AI가 각자 다른 선택을 한다. 나중에 합치려면 큰 비용이 든다.

| 항목 | 정할 내용 | 정하지 않으면 생기는 일 |
|---|---|---|
| **언어·프레임워크** | 백엔드(예: Python + FastAPI), 프론트엔드(예: React/Next.js), DB(예: PostgreSQL/SQLite) | A는 Flask, B는 Django로 만들어 와서 합칠 수 없게 된다 |
| **언어 버전** | 예: Python 3.12, Node 22 | 어떤 사람 PC에서만 실행된다 |
| **패키지 관리자** | 예: `uv`/`poetry`/`pip`, `npm`/`pnpm` + lock 파일 커밋 여부 | 의존성 버전이 사람마다 달라진다 |
| **폴더 구조** | 예: `crawler/`, `classifier/`, `api/`, `web/`, `docs/` | AI가 매번 새 폴더 구조를 만든다 |
| **코드 스타일 도구** | 포매터·린터(예: `ruff`, `prettier`, `eslint`)를 정하고 **자동 실행**되게 한다 | 기능 변경 없이 줄바꿈과 따옴표만 바뀐 커밋이 쏟아진다 |
| **핵심 데이터 구조** | "공지 1건"의 스키마 (아래 예시 참고) | 크롤러 담당과 분류 담당의 데이터 형식이 맞지 않는다 |
| **사용할 AI 도구** | 도구를 통일할지, 자유롭게 쓰되 규칙 파일만 공유할지 | 도구마다 읽는 설정 파일이 달라 규칙이 적용되지 않는다 (2절 참고) |
| **비용** | AI 구독료, LLM API 키(분류용)를 누가 어떻게 부담할지 | API 키 하나를 공유하다 사용량이 폭증하고, 누가 썼는지 알 수 없다 |

### 공지 데이터 스키마 예시 (팀이 합의해서 확정)

```yaml
notice:
  id: string            # 내부 ID
  source_id: string     # 수집 대상 게시판 ID (예: "computer.undergrad")
  bnum: int             # 게시판 번호
  bidx: int             # 글 번호 (중복 판정 키 후보)
  title: string
  url: string           # 원문 링크
  posted_at: date
  department: string    # 예: "컴퓨터공학과"
  category_tags: [string]   # 예: ["장학", "마감있음"]
  deadline: date | null     # 추정값
  deadline_confidence: low | high
  collected_at: datetime
```

**이 스키마처럼 여러 사람이 함께 쓰는 "약속"을 먼저 정하고, 그다음에 각자 AI로 구현한다.**

## 2. AI에게 줄 공통 맥락 만들기

### 2.1 규칙 파일을 저장소에 둔다

대부분의 AI 코딩 도구는 저장소 루트의 특정 파일을 자동으로 읽어서 프로젝트 규칙으로 쓴다.

| 도구 | 자동으로 읽는 파일 |
|---|---|
| Claude Code | `CLAUDE.md` |
| Cursor | `.cursor/rules/` 폴더, `AGENTS.md` |
| GitHub Copilot | `.github/copilot-instructions.md`, `AGENTS.md` |
| OpenAI Codex 등 | `AGENTS.md` |

> 도구별 파일 이름과 지원 여부는 바뀔 수 있으니 각 도구의 공식 문서로 한 번 확인한다.

**권장 방법**: 내용은 `AGENTS.md` 하나에 쓰고, 다른 파일은 그 파일을 가리키게만 한다. 그러면 규칙이 여러 곳으로 갈라지지 않는다. 예를 들어 `CLAUDE.md`에는 `@AGENTS.md` 한 줄만 쓴다.

### 2.2 규칙 파일에 들어갈 내용

```markdown
# 프로젝트 개요
서울과기대 공지 모아보기 서비스. 자세한 배경은 docs/ 참고.

# 기술 스택
- Python 3.12, FastAPI, SQLite / uv로 의존성 관리

# 폴더 구조
- crawler/: 수집 / classifier/: 분류 / api/: 서버 / web/: 프론트

# 명령어
- 설치: uv sync
- 테스트: uv run pytest
- 린트: uv run ruff check --fix

# 규칙
- 새 라이브러리를 추가하기 전에 사람에게 먼저 물어볼 것
- 공지 데이터는 docs/의 스키마를 따를 것
- 테스트에서 학교 서버에 실제 요청 금지. tests/fixtures/의 저장된 HTML 사용
- 공지 본문의 이메일·전화번호·학번은 저장 금지
- 기존 파일 전체를 다시 포맷하지 말 것
```

**짧고 구체적으로** 쓴다. AI는 "좋은 코드를 써라" 같은 막연한 말보다 "테스트 명령은 `uv run pytest`"처럼 바로 쓸 수 있는 정보를 잘 따른다.

### 2.3 규칙 파일은 코드처럼 관리한다

- 규칙 파일을 바꿀 때도 PR로 올리고 팀원 리뷰를 받는다. 한 사람이 바꾸면 모두의 AI 동작이 바뀌기 때문이다.
- AI가 같은 실수를 반복하면 그 실수를 막는 규칙을 한 줄 추가한다.
- 개인 취향 설정(응답 언어, 말투 등)은 공유 파일이 아니라 각자의 개인 설정 파일에 둔다. (예: Claude Code는 `CLAUDE.local.md`나 사용자 설정)

### 2.4 결정 사항을 기록한다

"왜 이 라이브러리를 골랐는지", "왜 첨부파일은 저장하지 않는지" 같은 결정은 `docs/decisions/`에 짧게 남긴다. 사람도 AI도 나중에 이 기록을 보고 같은 논의를 반복하지 않는다.

```markdown
# 0001. 중복 판정 키로 bidx 사용
- 날짜: 2026-11-XX
- 결정: ...
- 이유: ...
- 대안: 제목+날짜 유사도 (bidx가 전역 고유가 아닐 경우)
```

## 3. Git·GitHub 작업 규칙

AI를 쓰면 코드가 빠르게, 많이 생긴다. 그래서 Git 규칙이 느슨하면 충돌과 사고가 더 자주 난다.

### 3.1 기본 규칙

| 규칙 | 이유 |
|---|---|
| **`main`에 직접 push 금지**, 모든 변경은 PR로 | AI가 만든 코드가 리뷰 없이 들어가는 것을 막는다 |
| GitHub에서 **branch protection** 설정 (PR 필수, 리뷰 1명 이상, CI 통과 필수) | 규칙을 사람의 기억이 아니라 시스템으로 강제한다 |
| 브랜치 이름 규칙 (예: `feat/crawler-common`, `fix/date-parse`) | 누가 무엇을 하는지 한눈에 보인다 |
| **PR은 작게** (가능하면 변경 300줄 이하) | AI는 한 번에 수천 줄을 만들기 쉽지만, 그런 PR은 아무도 제대로 리뷰하지 못한다 |
| 작업 시작 전 `git pull`, 하루 한 번은 `main`을 자기 브랜치에 반영 | 오래된 브랜치일수록 충돌이 커진다 |
| `.gitignore`를 첫 커밋에 포함 (`.env`, `__pycache__/`, `node_modules/`, 수집 데이터 등) | 비밀정보나 대용량 파일이 커밋되는 것을 막는다 |

### 3.2 커밋 메시지

- 형식을 하나로 정한다. 예: `feat: 공통 CMS 파서 추가`, `fix: 날짜 파싱 오류 수정`
- AI 도구가 커밋 메시지에 `Co-Authored-By` 같은 서명을 자동으로 넣기도 한다. 넣을지 말지 팀에서 정한다.

### 3.3 PR 템플릿

`.github/pull_request_template.md`에 아래 같은 템플릿을 두면 리뷰가 쉬워진다.

```markdown
## 무엇을 바꿨나

## 어떻게 확인했나
- [ ] 로컬에서 테스트 통과
- [ ] 직접 실행해서 동작 확인

## AI 사용
- 사용한 도구:
- AI가 만든 부분 중 내가 이해하지 못한 부분이 있다면 적기:

## 리뷰어가 특히 봐 줬으면 하는 부분
```

## 4. 작업 나누기

### 4.1 파일이 겹치지 않게 나눈다

AI를 쓰면 한 사람이 짧은 시간에 여러 파일을 고친다. 두 사람이 같은 파일을 동시에 고치면 충돌이 크게 난다.

- **모듈(폴더) 단위로 담당을 나눈다.** 예: A = `crawler/`, B = `classifier/`, C = `api/` + `web/`
- 모듈 사이의 **경계(데이터 스키마, 함수 시그니처, API 명세)를 먼저 정하고 고정**한다. 그러면 각자 AI로 내부를 마음대로 구현해도 합칠 때 문제가 적다.
- 공용 파일(설정, 규칙 파일, 스키마)은 수정 전에 팀 채팅에 알린다.

### 4.2 이 프로젝트의 자연스러운 분할 예

```text
[수집] crawler/      → 게시판 목록·본문을 가져와 공지 스키마로 저장
   │ 공지 스키마 (합의된 약속)
[분류] classifier/   → 태그, 마감일 추정
   │ 분류 결과 스키마
[서비스] api/ + web/ → 조회, 관심사 설정, 알림
```

각 화살표 지점이 "약속"이다. 이 약속을 바꿀 때만 팀 전체가 논의한다.

### 4.3 작업 관리

- GitHub Issues로 할 일을 만들고 담당자를 지정한다. 하나의 이슈는 하나의 PR로 끝나는 크기로 나눈다.
- AI에게 작업을 시킬 때 이슈 내용을 그대로 붙여 넣으면, 요구사항이 사람과 AI 사이에서 일치한다.

## 5. 코드 리뷰와 품질

### 5.1 "AI가 썼다"는 핑계가 되지 않는다

- **PR을 올린 사람이 그 코드를 책임진다.** 내가 설명할 수 없는 코드는 올리지 않는다.
- 리뷰어가 "이 부분 왜 이렇게 했어?"라고 물었을 때 "AI가 그렇게 했어"가 답이 되면 안 된다.

### 5.2 AI 코드에서 특히 봐야 할 것

| 확인할 것 | 이유 |
|---|---|
| 존재하지 않는 함수나 라이브러리 | AI가 그럴듯한 이름을 지어내는 경우가 있다 |
| 요청하지 않은 변경 | 관련 없는 파일을 고치거나 전체를 다시 포맷하는 경우가 있다 |
| 테스트를 "고친" 방식 | 테스트를 통과시키려고 코드가 아니라 테스트의 기대값을 바꾸는 경우가 있다 |
| 예외 처리 누락, 또는 모든 에러를 무시하는 `except: pass` | 크롤러에서 특히 위험하다. 실패해도 아무도 모르게 된다 |
| 하드코딩된 값 | URL, API 키, 경로 등 |
| 불필요한 새 의존성 | 규칙 파일에 "추가 전 물어보기"를 넣어 둔다 |

### 5.3 자동 검사 (CI)

GitHub Actions로 PR마다 아래를 자동으로 돌린다.

- 린트·포맷 검사
- 테스트
- (선택) 비밀정보 검사: GitHub의 secret scanning·push protection을 켜거나 `gitleaks` 같은 도구를 쓴다.

사람이 매번 기억해서 확인하는 것보다, CI가 막게 하는 것이 훨씬 확실하다.

## 6. 보안·비밀정보·개인정보

| 규칙 | 설명 |
|---|---|
| **API 키·비밀번호는 절대 커밋하지 않는다** | `.env` 파일에 두고 `.gitignore`에 넣는다. 필요한 변수 이름만 적은 `.env.example`을 커밋한다. |
| **AI 대화창에 비밀 값을 붙여 넣지 않는다** | 대화 내용은 외부 서비스로 전송된다. |
| 키가 노출되면 **즉시 폐기하고 재발급** | 커밋을 지워도 Git 기록과 GitHub에 남는다. "지웠으니 괜찮다"가 아니다. |
| LLM API 키는 **사람마다 따로** 쓰거나 사용량 한도를 건다 | 누가 얼마나 썼는지 알 수 있고, 실수로 비용이 폭증하는 것을 막는다. |
| AI 도구의 **자동 실행 권한**에 주의 | AI가 명령을 자동으로 실행하는 모드에서는 파일 삭제, `git push --force` 같은 명령도 실행될 수 있다. 처음에는 승인 후 실행 모드로 쓰고, 익숙해진 뒤 범위를 넓힌다. |
| 실제 사용자 데이터나 개인정보를 AI에 붙여 넣지 않는다 | 디버깅할 때도 가짜 데이터로 바꿔서 쓴다. |

## 7. 이 프로젝트만의 주의점

### 7.1 개발 중 학교 서버에 요청이 몰리지 않게 한다

팀원 4~5명이 각자 AI에게 "크롤러 테스트해 줘"라고 하면, AI는 학교 서버에 반복해서 요청을 보낸다. 사람이 5명이면 요청도 5배가 되고, IP가 차단될 수 있다.

- **게시판 HTML 샘플을 한 번만 저장해 `tests/fixtures/`에 커밋**하고, 테스트와 개발은 이 파일로 한다.
- 실제 서버 요청은 정해진 사람이 정해진 때에만 한다. (예: 크롤러 담당이 하루 1~2회)
- 요청 간격과 User-Agent는 공통 설정 하나로 관리해서, 누가 실행해도 같은 규칙을 따르게 한다.
- 이 규칙을 `AGENTS.md`에도 적어 둔다. AI가 알아서 실제 서버로 테스트하는 것을 막을 수 있다.

### 7.2 공유 문서를 AI의 맥락으로 쓴다

`docs/`에 있는 문서를 AI에게 참고 자료로 주면, 같은 조사를 반복하지 않고 같은 사실을 바탕으로 작업한다.

| 문서 | 내용 |
|---|---|
| [notice-sources.md](notice-sources.md) | 수집 대상 게시판 목록, CMS 패턴, 중복 게시판, robots.txt 조사 결과 |

### 7.3 AI가 쓴 문서와 조사 결과도 검증한다

AI가 정리한 사실(URL, 날짜, 법 조항 등)은 틀릴 수 있다. 중요한 결정에 쓰기 전에 원문을 한 번 직접 확인한다. 실제로 처음에는 "`bidx`만으로 중복을 판정할 수 있다"고 추정했다. 그런데 검증해 보니 학과가 다시 올린 글은 새 `bidx`를 받아서, 그 방법만으로는 부족했다. ([research-findings.md](research-findings.md) 2.1절)

## 8. 처음 해보는 사람이 자주 겪는 문제

| 상황 | 대처 |
|---|---|
| AI가 만든 코드가 내 PC에서는 되는데 팀원 PC에서는 안 된다 | 언어 버전, lock 파일, `.env` 차이를 확인한다. README에 설치 방법을 정확히 적어 둔다. |
| 충돌(conflict)이 났는데 AI에게 "알아서 해결해"라고 했더니 남의 코드가 사라졌다 | 충돌 해결 결과는 반드시 직접 확인한다. 애매하면 그 코드를 쓴 팀원에게 물어본다. |
| AI가 대화가 길어지면서 앞에서 정한 규칙을 잊는다 | 작업 단위마다 새 대화를 시작한다. 중요한 규칙은 대화가 아니라 규칙 파일에 적는다. |
| AI가 "완료했습니다"라고 했는데 실제로는 동작하지 않는다 | 직접 실행하고 테스트를 돌려서 확인한다. AI의 "완료"는 검증이 아니다. |
| 같은 기능을 두 사람이 각자 AI로 만들었다 | 이슈에 담당자를 지정하고, 시작할 때 팀 채팅에 알린다. |
| AI가 내 의도와 다른 방향으로 크게 고쳤다 | 작게 나눠서 시킨다. "먼저 계획만 보여 줘"라고 한 뒤 확인하고 진행한다. 커밋을 자주 해 두면 되돌리기 쉽다. |
| 무엇을 물어봐야 할지 모르겠다 | AI에게 "이 코드가 무엇을 하는지 설명해 줘", "이 PR에서 위험한 부분이 있어?"처럼 이해와 검토 용도로도 적극적으로 쓴다. |
