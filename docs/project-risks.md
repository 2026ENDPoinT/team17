## 1. 기획·검증 단계 (현재)

| 문제 | 근거 / 이유 | 예방책 |
|---|---|---|
| **수요를 과대평가할 위험** | "공지를 놓친다"는 불편은 분명하지만, 학생 대부분은 본부 공지와 자기 학과 공지 정도만 본다. 게시판 140개를 모아도 한 사람에게 필요한 건 5~10개일 수 있다. | 주변 학생 10~20명에게 놓쳐서 손해 본 공지가 무엇이었는지, 지금은 공지를 어떻게 확인하는지 물어본다. 핵심 가치가 "모아보기"인지 "마감 알림"인지 정한다. |
| **범위가 너무 넓음** | 수집 대상 140개, 파서 패턴 2~3종, 분류, 알림까지 한 번에 하면 팀 프로젝트 기간 안에 끝내기 어렵다. | MVP 범위를 지금 확정한다. 예: 본부 게시판 5개 + 팀원 학과 3~4곳 + 키워드 알림. |
| **서비스 형태 미정** | 웹, 앱, 카카오톡 채널, 디스코드 봇 중 무엇을 고르냐에 따라 알림 구현 난이도와 비용이 크게 달라진다. 카카오 알림톡은 사업자 등록과 비용이 필요하다. | 알림 채널부터 고른다. 빠르게 검증하려면 웹 + 이메일, 또는 텔레그램/디스코드 봇이 가장 쉽다. |
| **학교와의 관계** | robots.txt로 막혀 있지는 않지만, 학교가 서비스를 알게 된 뒤 문제를 삼을 수 있다. | 서비스 이름에 학교 공식 명칭이나 로고를 쓰지 않는다. 정식 운영 전에 정보전산원 등 학교 쪽에 알리는 일정을 계획에 넣는다. |

## 2. 수집(크롤러) 개발 단계

| 문제 | 근거 | 예방책 |
|---|---|---|
| **예외 사이트** | 건축학전공(archidesign)은 별도 PHP CMS이고 날짜 형식이 `26.10.26`이다. 취업진로본부 채용공고는 일반 게시판 형식이 아니며, 추천채용은 목록을 읽지 못했다. | 공통 CMS 파서 하나를 먼저 만들고, 예외 사이트는 MVP에서 뺀다. (notice-sources.md 4.3절에 예외 목록이 정리돼 있음) |
| **상단 고정 공지** | 고정 공지가 목록 맨 위에 있어 "최신 글" 판정이 틀어질 수 있다. 국제대학 목록에는 `2029-12-31` 같은 이상한 날짜도 있었다. | 새 글 판정 기준을 날짜가 아니라 **`bidx`(글 ID)를 처음 보는지 여부**로 잡는다. |
| **중복 공지** | 미러 게시판은 같은 `bidx`를 쓰지만, 학과가 다시 올린 글은 새 `bidx`를 받는다. 실측 결과 한 달에 제목이 완전히 같은 사본만 82건이었고, 한 공지가 10개 학과에 올라온 경우도 있었다. 제목이 조금 다른 사본도 많다. | `bidx` 일치 → 정규화한 제목 유사도 순으로 묶는다. research-findings.md 6.2절의 실제 사례로 임계값을 테스트한다. |
| **글 수정** | 올라온 뒤 제목에 "(마감)", "신청기한 연장", "(장소변경)"이 붙는 경우가 한 달에 18건 있었다. 상세 페이지에 수정일이 없다. | 최근 14일 글은 하루 한 번 다시 읽고, 제목·본문 해시가 바뀌면 갱신한다. 마감 연장 같은 변경은 알림 대상이 될 수 있다. |
| **페이지 파라미터 함정** | 링크에 보이는 `nowpage`는 무시되고 `page`만 동작한다. 잘못 쓰면 에러 없이 1페이지만 반복 수집한다. | `page`를 쓰고, 2페이지의 글 ID가 1페이지와 다른지 확인하는 테스트를 둔다. |
| **해외 IP 차단 가능성** | GitHub Actions 러너는 해외 데이터센터에서 돈다. 국내 대학 사이트 중에는 해외 IP를 막는 곳이 있다. (아직 확인 안 함) | 개발 초기에 GitHub Actions에서 목록 페이지 1개를 요청하는 테스트를 한 번 돌린다. |
| **차단·서버 부담** | 학교 서버는 요청이 몰리면 IP를 차단할 수 있다. 연구처·산학협력단(iac)처럼 TLS 설정이 다른 서버도 있다. | 호스트당 요청 간격을 두고, 실패하면 간격을 점점 늘려 재시도한다. User-Agent에 서비스 이름과 연락처를 넣는다. 조회 주기는 하루 몇 번이면 충분하다. |
| **본문이 비어 있음** | 표본 180건 중 18%는 본문 텍스트가 100자 미만이다. 그중 포스터 이미지만 있는 글이 13%, 첨부(HWP·PDF)만 있는 글이 7%다. | MVP에서는 제목과 본문만 쓰고 이런 글은 "원문 보기"로 넘긴다 (약 80%는 처리됨). 2단계에서는 첨부 추출보다 포스터 이미지 인식을 먼저 검토한다. |
| **로그인 안의 공지** | 비교과 시스템(EPiC), 교수학습개발센터 공지, 추천채용은 로그인해야 보인다. | 수집하지 않는다. 학생 계정을 대신 쓰는 방식은 개인정보·보안 문제가 커서 피한다. 서비스 소개에 "공개 게시판만 모은다"고 밝힌다. |

## 3. 분류·가공 단계

| 문제 | 근거 | 예방책 |
|---|---|---|
| **분류 기준이 모호함** | "[THE-BEAR] 행정학과 현직자 특강 '로스쿨 진학준비'"는 취업, 행사, 학과 공지 중 어디일까? 한 공지가 여러 카테고리에 걸친다. | 카테고리를 단일 선택이 아닌 **태그(다중 선택)**로 설계한다. 실제 공지 100건 정도를 뽑아 팀원이 직접 태깅해 보면 분류 기준과 평가 데이터가 함께 생긴다. |
| **마감일 추출 오류** | 날짜 표기가 "~11/12 18시까지", "26.11.26.(목)", "(~11/20(금)까지)"처럼 제각각이다. 마감일을 잘못 알려주면 신뢰를 바로 잃는다. | 추출한 마감일은 확정값이 아니라 "추정"으로 표시하고, 항상 원문 링크를 같이 보여준다. |
| **LLM 비용·속도** | LLM으로 분류하면 공지 1건당 비용이 든다. 실측한 신규 공지는 학부 기준 하루 약 16건이고 본문 중앙값은 492자라 부담이 크지 않다. 다만 과거 글을 한꺼번에 처리하면 커질 수 있다. | 키워드 규칙으로 먼저 거르고, 애매한 것만 LLM에 보낸다. 과거 데이터는 최근 몇 달 치만 처리한다. |

## 4. 서비스·알림 개발 단계

| 문제 | 근거 | 예방책 |
|---|---|---|
| **개인정보가 노출될 위험** | 장학생 선발 결과, 전과·복수전공 선발 결과 공지에는 이름이나 학번이 들어간 경우가 있다. 홈페이지의 이메일 주소를 자동 수집하는 것은 정보통신망법 제50조의2로 금지돼 있다. | 본문 전체를 복제하지 않고 제목, 요약, 원문 링크만 보여준다. 첨부파일은 저장하거나 다시 배포하지 않는다. 이메일, 전화번호, 학번 패턴은 수집 단계에서 지운다. |
| **사용자 정보 관리** | 사용자의 학과, 관심사, 알림 수신 정보도 개인정보다. | 꼭 필요한 정보만 받고, 학번이나 실명은 받지 않는다. 출시 전에 간단한 개인정보처리방침을 준비한다. |
| **알림 피로** | 관심 키워드를 넓게 잡으면 알림이 하루 수십 개가 되고, 사용자는 바로 알림을 끈다. | 기본값은 "하루 1회 요약"으로 두고, 마감 임박 등 중요한 것만 즉시 알림으로 보낸다. |

## 5. 출시·운영 단계

| 문제 | 근거 | 예방책 |
|---|---|---|
| **조용한 수집 실패** | 사이트 구조가 바뀌면 크롤러가 에러 없이 0건을 수집할 수 있다. 사용자는 "공지가 없다"고 오해한다. | 게시판별로 마지막 수집 성공 시각과 신규 글 수를 기록한다. "활발" 게시판에서 며칠째 0건이면 경고가 오게 한다. |
| **서버 비용과 상시 운영** | 크롤러는 계속 돌아야 하므로 팀원 PC로는 운영할 수 없다. | GitHub Actions 예약 실행이나 무료·저가 클라우드로 시작할 수 있는지 미리 확인한다. |
| **책임 소재** | 서비스가 공지를 놓쳐서 사용자가 장학금 신청을 못 하면 원망은 서비스로 온다. | "공식 공지를 대체하지 않는다"는 고지를 넣고, 화면에 수집 시각을 표시한다. |

## 6. 유지보수·확장 단계

| 문제 | 근거 | 예방책 |
|---|---|---|
| **학과 개편** | 기계시스템공학부가 2025년에 재구조화됐고, 기계시스템디자인공학과와 기계·자동차공학과는 2032년까지만 존속한다. 학과와 사이트가 해마다 바뀐다. | 수집 대상 목록을 코드에 하드코딩하지 않고 **설정 파일(YAML/JSON)**로 분리한다. notice-sources.md가 그 원본이 될 수 있다. 학기마다 목록을 점검한다. |
| **휴면 게시판** | 지식재산교육선도대학사업단(마지막 글 2019년), 영어영문학과 대학원 공지(2015년) 등은 사실상 쓰지 않는 게시판이다. | 수집 목록에 상태 필드를 두고, 휴면 게시판은 처음부터 제외한다. |
| **팀 해산 후 방치** | 팀 프로젝트가 끝나면 아무도 관리하지 않아 잘못된 정보가 계속 나갈 수 있다. | 종료 계획(운영 중단 공지, 데이터 삭제)을 미리 정한다. |
