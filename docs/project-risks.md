# 장학금 헌터: 프로젝트 위험 요소와 대응

> 작성일: 2026-11-13 (사전 조사 단계의 위험 문서와 장학금 비교 서비스 분석을 하나로 합침)
> 서비스: 서울과기대 교내 게시판의 장학금 공지를 모아 **조건·금액을 비교**하고, **가성비·마감일 순 정렬**과 **필터링**을 제공한다. 범위와 단계 계획은 [scholarship-mvp.md](scholarship-mvp.md)를 따른다.
> 근거: 게시판 136개의 30일치 목록 실측과, 그 기간 장학금 관련 공지 76건의 본문 분석. ([research-findings.md](research-findings.md) 6절)
> 확인 수준: **직접 확인** / **추정**

## 한눈에 보기

가장 큰 문제는 기술이 아니라 **데이터**다.

1. **금액이 공지 본문에 거의 없다.** 76건 중 본문에서 금액을 찾은 글은 18건(24%)이다. 그중 8건은 같은 가족장학생 공지의 사본이라, 서로 다른 장학금으로 치면 약 11종이다. 첨부가 있는 글은 61건(80%)이고, 금액이 없는데 첨부가 있는 글이 45건이다. 금액은 대부분 **HWP·PDF 첨부 안에 있다**고 봐야 한다. (본문은 직접 확인, 첨부 안의 금액은 추정)
2. **금액끼리 비교가 안 된다.** "등록금 50% 감면", "250만원", "시급 10,320원", "등록금 전액"이 섞여 있다. 하나의 숫자로 줄 세우려면 기준을 우리가 정해야 한다. (직접 확인)
3. **"가성비"의 분모(들이는 노력, 붙을 확률)를 알 수 없다.** 경쟁률과 선발 인원은 거의 공개되지 않는다. (추정)
4. **공식 앱이 장학 공지 푸시를 이미 한다.** 스마트캠퍼스 앱 메뉴에 장학 공지가 있다. 장학금 "알림"만으로는 차별점이 없고, **비교·정렬·자격 필터**가 차별점이다. ([research-findings.md](research-findings.md) 1.1절)

그래서 처음부터 자동 추출만으로 비교표를 만들기는 어렵다. 해커톤 MVP는 **"자동 수집 + 사람이 검수해서 채우는 비교표"**로 시작하는 것이 현실적이다. ([부록](#부록-해커톤-기준-현실적인-접근))

## 1. 기획 단계: 비교와 가성비의 정의

| 문제 | 근거 | 대응 |
|---|---|---|
| **신청할 수 없는 공지가 섞여 있다** | 76건에는 결과 발표, 지급 완료, 등록금 분할납부, 서약서 제출 안내도 들어 있다. | 공지를 `모집`, `결과·지급`, `납부·행정`으로 먼저 나누고, 비교표에는 `모집`만 넣는다. |
| **금액 단위가 제각각이다** | 일시금(250만원), 등록금 비율(50% 감면, 전액), 시급(근로장학 10,320원), "예산 범위 내 차등"이 섞여 있다. | 유형별로 따로 보여 준다(일시금 / 등록금 감면 / 근로). 하나로 환산하려면 "학기당 받는 금액 추정치"처럼 기준을 명시하고 근거를 보여 준다. |
| **금액이 사람마다 다르다** | "등록금 50%"는 학과별 등록금에 따라 실제 금액이 달라진다. | 학과별 등록금 표가 있어야 원화로 환산할 수 있다. 없으면 "%"로만 표시한다. |
| **가성비 분모를 알 수 없다** | 경쟁률·선발 인원은 거의 공개되지 않는다. 확인할 수 있는 건 제출 서류(자기소개서, 추천서), 면접 여부, 봉사·근무 의무 정도다. | "가성비"를 **금액 ÷ 준비 부담**으로 정의한다. 준비 부담은 서류 수, 면접 여부, 의무 활동으로 점수화하고, 계산 방식을 화면에 공개한다. |
| **중복 수혜 제한** | 76건 중 16건(21%)이 중복 수혜·타 장학금 관련 문구를 담고 있다. 금액 1, 2위 장학금을 같이 받을 수 없는 경우가 있다. | 장학금마다 "중복 수혜 제한 있음"을 표시한다. 조합 추천은 하지 않는다. |
| **양이 적고 계절을 탄다** | 30일 동안 장학금 관련 글은 76건, 서로 다른 장학금은 약 56종이다. 결과·납부 안내를 빼면 모집 공지는 더 적다. 측정한 때가 학기 중간이라, 개강 전후에는 더 많을 수 있다. | 비교 기능은 열려 있는 장학금이 충분할 때 의미가 있다. 데모 시점에 적으면 지난 공지까지 포함한 "아카이브 비교"로 보여 준다. |
| **학생이 원하는 "가성비"가 다를 수 있다** | 금액, 준비 부담, 붙을 확률 중 무엇을 중시하는지 아직 모른다. | 팀원과 친구 몇 명에게 물어보고 정렬 기준을 정한다. (7절) |
| **학교와의 관계** | robots.txt로 막혀 있지는 않지만, 장학 담당 부서는 잘못된 정보가 퍼지거나 문의가 늘어나는 것을 우려할 수 있다. | 서비스 이름에 학교 공식 명칭이나 로고를 쓰지 않는다. 정식 운영을 하려면 학생지원과(장학 담당)에 미리 알린다. 담당자가 정보를 확인해 주면 신뢰도가 오히려 오른다. |

## 2. 수집 단계

| 문제 | 근거 | 대응 |
|---|---|---|
| **31개 게시판에 흩어져 있다** | 본부 장학공지에는 30%만 있다. 학과에만 올라온 장학금도 있다(전기공사공제조합장학회, 산업보건분야 장학생 등). ([scholarship-mvp.md](scholarship-mvp.md) 2절) | v1부터 학과 게시판을 포함한다. 목록 1페이지만 읽으면 되므로 비용은 거의 늘지 않는다. |
| **같은 장학금이 여러 번, 다른 제목으로 올라온다** | 가족장학생 공지는 학과 8곳 이상에 올라왔다. 본부 글은 "(통정시 신청, 2026. 10. 23.~11. 6.) 2026. 2학기 2차 어의 및 가족…"처럼 제목 형식이 다르다. 학과가 다시 올린 글은 새 `bidx`를 받는다. | `bidx` 일치 → 정규화한 제목 유사도 → 사람 검수 순으로 묶는다. 묶지 않으면 비교표에 같은 장학금이 여러 줄로 나온다. |
| **학과 마감이 본부와 다를 수 있다** | 학과가 서류를 모아 본부에 내는 경우 학과 마감이 더 빠를 수 있다. (추정) | 같은 장학금이라도 게시판별 마감일을 따로 저장하고, 가장 이른 날짜를 기준으로 알린다. |
| **키워드로 못 잡는 장학금** | "취업준비 멘토링(장학금 지급)"처럼 장학금이 부수적인 프로그램이 있다. | 키워드 목록을 놓친 사례로 계속 보강한다. |
| **글 수정** | 올라온 뒤 제목에 "(마감)", "신청기한 연장", "(장소변경)"이 붙는 경우가 한 달에 18건 있었다. 상세 페이지에 수정일이 없다. | 열려 있는 장학금은 하루 한 번 다시 읽어 제목·본문 해시를 비교한다. 마감 연장은 알림 대상이다. |
| **페이지 파라미터 함정** | 링크에 보이는 `nowpage`는 무시되고 `page`만 동작한다. 잘못 쓰면 에러 없이 1페이지만 반복 수집한다. | `page`를 쓰고, 2페이지의 글 ID가 1페이지와 다른지 확인하는 테스트를 둔다. |
| **예외 사이트·고정 공지** | 건축학전공은 별도 CMS이고, 카드형 목록을 쓰는 게시판도 있다. 고정 공지가 목록 위에 있어 "최신 글" 판정이 틀어질 수 있다. | 새 글은 "처음 보는 `bidx`인가"로 판정한다. 예외 사이트는 MVP에서 뺀다. ([notice-sources.md](notice-sources.md) 4.3절) |
| **차단·서버 부담** | 학교 서버는 요청이 몰리면 IP를 차단할 수 있다. | 호스트당 요청 간격 1초 이상, 실패 시 간격을 늘려 재시도한다. 개발·테스트는 저장한 HTML(fixture)로 한다. |
| **해외 IP 차단 가능성** | GitHub Actions 러너는 해외 데이터센터에서 돈다. (아직 확인 안 함) | 개발 초기에 GitHub Actions에서 목록 페이지 1개를 요청하는 테스트를 한 번 돌린다. |
| **로그인 안의 정보** | 비교과 시스템(EPiC), 교수학습개발센터 공지, 추천채용은 로그인해야 보인다. | 수집하지 않는다. 학생 계정을 대신 쓰는 방식은 피한다. |

## 3. 정보 추출·분류 단계

이 서비스에서 가장 어려운 부분이다.

| 문제 | 근거 | 대응 |
|---|---|---|
| **금액과 조건이 첨부 안에 있다** | 장학금 공지의 80%에 첨부가 있다(전체 공지는 47%). 형식은 PDF 58개, HWP 55개, HWPX 7개, XLSX 9개이고 글당 평균 1.8개다. | 첨부 분석을 나중으로 미룰 수 없다. **PDF와 HWP 텍스트 추출이 v0~v1 범위에 들어온다.** 후보 라이브러리는 [research-findings.md](research-findings.md) 5.1절에 있다. |
| **첨부가 공고문만 있는 게 아니다** | 파일 이름으로 보면 신청서·동의서·추천서 양식이 30개, 공고·안내문이 39개다. | 파일 이름으로 공고문을 먼저 고르고, 양식 파일은 분석하지 않는다. |
| **HWP 추출이 깨질 수 있다** | HWP는 표 안에 금액·자격이 들어가는 경우가 많고, 라이브러리마다 표 처리 품질이 다르다. (추정) | 해커톤 시작 전에 실제 공고 HWP 5~10개로 라이브러리를 시험한다. |
| **본문이 거의 없는 공지** | 본문 텍스트가 100자 미만인 글이 76건 중 18건(24%)이다. 포스터 이미지만 있거나 첨부만 있는 글이다. | 첨부는 위 방법으로 처리한다. 이미지 속 글자는 OCR이나 비전 모델이 필요하니, MVP에서는 "원문 확인 필요"로 표시한다. |
| **LLM이 금액을 지어낼 위험** | 추출을 LLM에 맡기면 원문에 없는 숫자를 만들 수 있다. | 추출한 값마다 **원문 근거 문장**을 같이 저장하고, 그 문장에 숫자가 실제로 있는지 코드로 확인한다. 근거가 없으면 비워 둔다. |
| **조건 표현이 모호하다** | "직전 학기 성적 우수자", "가계 곤란 학생" 같은 표현이 많다. 본문에서 찾은 조건은 학년·학기 50건, 서류·면접 33건, 성적 20건, 학과 13건, 소득 9건, 거주지 8건이다. | 조건을 "확실한 조건"(학년, 학과, 거주지)과 "판단이 필요한 조건"(성적 우수, 가계 곤란)으로 나눈다. |
| **마감일 형식이 다양하다** | "~11/12 18시까지", "2026. 10. 23.~11. 6.", "(마감)"처럼 표기가 다르다. 제목에 마감 표현이 있는 장학금 글은 33%다. | 마감일은 시각까지 저장한다. 파싱하지 못하면 "마감일 확인 필요"로 두되, 마감 임박 정렬에서는 빠지지 않게 한다. |
| **LLM 비용** | 장학금 공지는 한 달 수십 건이라 비용 부담은 작다. 첨부까지 넣으면 입력이 길어진다. | 키워드 규칙으로 먼저 거르고, 공고문 첨부만 LLM에 보낸다. |

## 4. 필터·정렬·알림 단계

| 문제 | 근거 | 대응 |
|---|---|---|
| **필터가 틀리면 받을 수 있는 장학금을 숨긴다** | 자격 추출이 틀려 해당되는 장학금이 걸러지면 학생은 존재조차 모른다. 잘못 보여 주는 것보다 잘못 숨기는 쪽이 손해가 크다. | 기본 동작을 "숨기기"가 아니라 "해당 가능성 높음 / 확인 필요 / 해당 안 됨" 3단계 표시로 한다. |
| **자격 정보가 민감하다** | 소득분위, 거주지, 장애 여부를 입력받아야 필터가 의미 있다. 장애 여부는 개인정보보호법상 민감정보다. | 자격 정보는 **기기 안에만** 저장하고 필터링도 기기에서 한다. 학번·실명은 받지 않는다. ([scholarship-mvp.md](scholarship-mvp.md) 4절) |
| **정렬 기준이 오해를 낳는다** | "가성비 1위"를 보고 지원했다 떨어지면, 학생은 서비스가 추천했다고 느낀다. | 순위 옆에 계산 근거(금액, 준비 부담 점수)를 보여 주고, "선발 가능성은 반영하지 않음"을 명시한다. |
| **공지 속 개인정보** | 장학생 선발 결과·제적 안내에는 마스킹된 이름 명단이 있다. 본문의 16%에 이메일, 18%에 전화번호가 있다. | 본문 전체를 다시 보여 주지 않는다. 제목, 추출한 비교 항목, 원문 링크만 보여 준다. 첨부는 저장·재배포하지 않는다. |
| **알림 채널** | 카카오 알림톡은 사업자 등록이 필요하다. | 웹 푸시, 이메일, 디스코드/텔레그램 봇 중 하나로 시작한다. ([research-findings.md](research-findings.md) 4절) |
| **알림 피로** | 조건을 넓게 잡으면 알림이 많아지고 사용자는 알림을 끈다. | 기본값은 "마감 임박 + 새 장학금 하루 1회 요약"으로 둔다. |

## 5. 출시·운영 단계

| 문제 | 근거 | 대응 |
|---|---|---|
| **사람 검수가 필요하다** | 자동 추출만으로는 금액·조건 정확도를 보장할 수 없다. | 한 달 50~60종이면 한 사람이 하루 몇 분씩 검수할 수 있다. 검수 화면(추출값 + 원문 근거 + 승인 버튼)을 기능에 넣는다. |
| **조용한 수집 실패** | 사이트 구조가 바뀌면 크롤러가 에러 없이 0건을 수집할 수 있다. | 게시판별 마지막 수집 성공 시각과 신규 글 수를 기록한다. 본부 장학공지에서 며칠째 0건이면 경고가 오게 한다. |
| **틀린 정보에 대한 책임** | 금액·마감이 틀려 손해를 봤다는 항의가 올 수 있다. | "공식 공지를 대체하지 않는다"는 고지, 수집·검수 시각, 원문 링크를 모든 장학금에 붙인다. 오류 신고 버튼을 둔다. |
| **서버 비용과 상시 운영** | 크롤러는 계속 돌아야 하므로 팀원 PC로는 운영할 수 없다. | GitHub Actions 예약 실행이나 무료·저가 클라우드로 시작한다. 처리량이 작아 비용은 크지 않다. |
